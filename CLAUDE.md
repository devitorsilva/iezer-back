# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Backend API for the iEzer platform (church management: registrations, finance, reports). Fastify 5 + Prisma 6 + Postgres on Supabase, deployed on Render. Node 22, ESM (`"type": "module"`). Domain language is Portuguese (routes, enums, user-facing messages); code identifiers are English.

Companion frontend lives in a separate repo, `iezer-front`: the church app (Vite on 5173) and, since Sprint 16, the iEzer team back-office app (`npm run dev:admin` on 5174, the default `ADMIN_WEB_ORIGIN`).

## Commands

```bash
npm install            # also runs `prisma generate` (postinstall)
npm run dev            # tsx watch src/server.ts → http://localhost:3333
npm run build          # tsc → dist/
npm start              # node dist/server.js
npm run typecheck      # tsc (lint is the same command; no ESLint/formatter configured)
npm run prisma:migrate # prisma migrate dev
npm run prisma:push    # prisma db push
npm run prisma:studio
```

There is no test suite yet. CI (`.github/workflows/ci.yml`) runs `npm run lint`, `typecheck` and `build` on pushes to `main`/`develop` and on PRs.

Healthchecks: `GET /health` and `GET /healthz` (the latter used by Render).

## Environment

`src/config/env.ts` validates `process.env` with Zod at import time — the app crashes on startup if `DATABASE_URL`, `DIRECT_URL`, `SUPABASE_URL` or `BETTER_AUTH_SECRET` (32+ chars) are missing. `BETTER_AUTH_URL` is the API origin as the browser sees it (in production, the front's domain, which proxies `/api/*` to Render). `SUPABASE_SERVICE_ROLE_KEY` (and `SUPABASE_STORAGE_BUCKET`, default `iezer-documentos`) enable account documents in Storage. `RESEND_API_KEY`/`EMAIL_FROM` are optional: without a key, transactional e-mails (`src/lib/mailer.ts`) are logged (with links in dev) instead of sent. `RESEND_WEBHOOK_SECRET` (`whsec_...`) enables the public Resend webhook `POST /api/webhooks/resend` (503 without it). `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` are optional (Google login off without them; authorized redirect = `BETTER_AUTH_URL` + `/api/auth/callback/google`). Links in e-mails point to `WEB_ORIGIN`. See `.env.example`. `DATABASE_URL` is the Supabase pooler (pgbouncer); `DIRECT_URL` is used by Prisma for migrations. `WEB_ORIGIN` (church app) and `ADMIN_WEB_ORIGIN` (team back-office app; links in team e-mails) are the allowed CORS origins and Better Auth `trustedOrigins`; `localhost`/`127.0.0.1` on ports 5170–5179 are always allowed (`src/app.ts`).

## Architecture

- `src/server.ts` → `buildApp()` in `src/app.ts` (CORS, `@fastify/sensible`, global error handler that maps Supabase/Prisma connection failures to 503 with Portuguese messages).
- All business routes are mounted under `/api` via `src/modules/index.ts`. `/auth/*` is the Better Auth handler (public, config in `src/lib/auth.ts`; password reset with hashed tokens, sign-up disabled, a `user.create.before` hook that requires a valid invite) and `/convites/:token` is the public invite page/acceptance (`src/modules/convites/`, IP rate limit in `src/lib/rate-limit.ts`); everything else is registered inside a scope with the `requireSession` hook (`src/lib/require-session.ts`: 401 without session, 403 `USER_INACTIVE` for non-ATIVO users, 403 `TWO_FACTOR_REQUIRED` for a Google session still waiting for the 2FA code, 403 `TWO_FACTOR_SETUP_REQUIRED` outside `/api/me` for users with a protected permission and no 2FA (`src/lib/two-factor.ts`), 403 `CHURCH_SUSPENDED` (with `churchStatus`) everywhere, `/api/me` included, for church accounts of a SUSPENSA/ENCERRADA church (`src/lib/church-status.ts`; also refused at login in `session.create.before`, on invite pages and for support grants); sets `request.user`/`request.session`): `/me`, `/cadastro`, `/financeiro`, `/relatorios`, `/modulos` (placeholders for planned modules). Each business module's `routes.ts` exposes a `GET /overview` and registers its sub-sections.
- API contract (routes added since Sprint 2): `docs/api-contrato.md`. Test users: `npm run user:create -- <email> <nome> <senha> [status]` (public sign-up is disabled).
- Data routes (`/pessoas`, `/cadastro`, `/financeiro`, `/relatorios`, `/organizacao`, `/acesso/{perfis,convites,usuarios,onboarding,auditoria}`) sit in a nested scope with `resolveOrganization` (`src/lib/access.ts`): 403 `TERMS_REQUIRED` until the user accepts the current `TERMS_VERSION` (`src/lib/terms.ts`, `POST /me/termos`); active org from `X-Organization-Id` (+ `X-Organization-Scope: todas` from the sede), checked against the user's assignments; sets `request.access`. Church-wide actions use `requireChurchPermission` (permission at the sede); cross-org screens filter with `organizationIdsWith`. Access writes (profiles, assignments, user status, invite acceptance) go through `runGuarded` in `src/modules/acesso/travas.ts` (protected-permission checks, last-admin lock, notice e-mails after commit). Each route declares `{ preHandler: requirePermission("key", ...) }` (any-of). Controllers pass `getRequestContext(request)` (church id, read/write org ids, permissions, audit actor) to services. Business errors throw `AppError(status, code, message, details?)`; the global handler sends `{ statusCode, code, message, ...details }` and maps `ZodError` to 400 `VALIDATION_ERROR`. Permission catalog: `src/modules/acesso/permissoes/catalog/` (one file per module). Test access: `npm run acesso:seed`, `npm run user:assign -- <email> <PASTOR|TESOUREIRO|SECRETARIO> [slug]`. New church + first admin invite: back-office screen (`POST /api/admin/igrejas`, `createChurch` in `src/modules/admin/igrejas/criacao.ts`); the `igreja:criar` script is gone.
- Auth security (Sprint 12, `src/lib/auth.ts`): Google login (only for an active user or a valid invite; the first Google login consumes the invite in `session.create.before`), `twoFactor` plugin (TOTP, e-mail code, backup codes) — Google does **not** skip the iEzer 2FA, so Google sessions of 2FA users start with `Session.twoFactorPending` and are released by the plugin's `verify-*` endpoints. Better Auth routes for password, e-mail, sessions and accounts are closed to the browser (`BLOCKED_PATHS`); the iEzer versions live in `/api/me/*` (`src/modules/me/conta/`) and call `auth.api` internally; swapping the authenticator app (the plugin refuses a second enable and mandatory 2FA cannot be disabled) is `POST /api/me/2fa/reconfigurar`. Per-email login lock in `src/lib/login-lock.ts`; account security events (audit + alert e-mail) via `recordAccountEvent` (`src/lib/account-events.ts`).
- iEzer team (Sprint 15, `src/lib/team.ts`, PRD `docs/prd/backoffice.md`): a team account is a `User` without person or assignments plus a `TeamMember` (`roles`: ADMINISTRADOR, SUPORTE, IMPLANTACAO; ADMINISTRADOR implies all). Status is `User.status`; pending invites live in `TeamInvite` (hash, 72h). `requireSession` loads `request.team` and, for team sessions, enforces 12h idle (`Session.lastActiveAt`, 401 `SESSION_IDLE`) and TOTP-only 2FA (e-mail OTP refused with `TEAM_TOTP_ONLY` in `src/lib/auth.ts`; Google refused). Team logins and lockouts e-mail every active ADMINISTRADOR (`src/lib/team-emails.ts`). `/api/admin/*` (`src/modules/admin/`) uses `requireTeamSession` (403 `TEAM_ACCOUNT_REQUIRED` for church accounts, team terms `TEAM_TERMS_VERSION`) and `requireTeamRole(...)` per route (support requests in `admin/pedidos/`); public team invite at `/api/admin/convites/:token`. Team actions without a church audit with `organizationId: null`, module `BACKOFFICE`, actor `SUPORTE`. Church and team e-mails are mutually exclusive (`isTeamEmail` in `assertLoginEmailAvailable`). First ADMINISTRADOR: `npm run suporte:agente -- <email> "<nome>"` (only while there is no active admin; then invites via `/api/admin/equipe`). Churches (Sprint 17, `src/modules/admin/igrejas/`): list, create, detail, edits (reusing `OrganizationService` with a `{ churchId, actor }` context) and admin invite resend with reason; team actions on a church audit on that church as `SUPORTE`, and the team never receives invite links nor person data beyond B8. Sprint 18: church status changes in `admin/igrejas/situacao.ts` (activate needs an active admin; suspend deletes the church's sessions; reactivate goes back to ATIVA, or IMPLANTACAO without admin) and account owner change with a document in `admin/igrejas/responsavel.ts` (`AccountDocument` + `AccountOwnerChange`; file in base64 JSON, type sniffed by content, uploaded to Supabase Storage before the transaction and removed if it fails; signed links of 5 min, each opening logged). Storage client in `src/lib/storage.ts` (REST + `SUPABASE_SERVICE_ROLE_KEY`, private bucket `SUPABASE_STORAGE_BUCKET`; 503 `STORAGE_UNAVAILABLE` without the key).
- Support access (Sprint 13, reworked in Sprint 19, `src/lib/support.ts`, PRD `docs/prd/backoffice.md` B9/B15): a `SupportGrant` belongs to the team, not to one agent. Requests live in `/api/admin/pedidos` (`src/modules/admin/pedidos/`): read-only goes straight to the church (`PENDENTE`), write and emergencies wait for an ADMINISTRADOR (`AGUARDANDO_IEZER`, `internalApprovedBy`), who never approves their own request; IMPLANTACAO-only members request read-only and only for churches in IMPLANTACAO. Durations 24h default / 72h max (emergency 24h), starting at the church approval; `PENDENTE` without answer for 7 days shows as `EXPIRADO` (`grantStatus`, no job). The church side is `src/modules/acesso/suporte/` (`/api/acesso/suporte`, hides `AGUARDANDO_IEZER`). Actions without data access (B9: reset an admin's 2FA, unlock login, recover admin) are in `admin/igrejas/acoes.ts`, role SUPORTE, with reason/ticket, `teamActionNotice` to the account owner and audit as `SUPORTE` on the church. Support mode (RF-BO38): a team account only gets church data through `resolveOrganization` with an active grant (`loadSupportOrganizations(roles)`: SUPORTE/ADMINISTRADOR any grant, IMPLANTACAO-only read grants of IMPLANTACAO churches), checks the team terms instead of `TERMS_VERSION`, and gets 403 `SUPPORT_NO_GRANT` otherwise; `GET /api/me` returns `user.isTeamAccount`. Permissions are the catalog keys of the grant scope minus pastoral notes and `acesso.suporte.autorizar`; `request.access.support` is set and `getRequestContext` uses actor `SUPORTE`. Read-only grants reject non-GET (`SUPPORT_READ_ONLY`); `/api/acesso` and `/api/organizacao` writes are always blocked; mark a route `{ config: { denySupport: true } }` to close it to support (pastoral notes). Every support GET is logged as `suporte_ler` in a `preHandler` (`src/lib/support-log.ts`). The back-office opens the church app at `/app?igreja=<id>` (front env `VITE_APP_URL`/`VITE_ADMIN_URL`).
- Health panel and team e-mails (Sprint 20): `GET /api/admin/painel` (`src/modules/admin/painel/`, all roles) runs one aggregated SQL per alert (no admin, one admin, Implantação over 15 days, rejected e-mail in 7 days, login locked now, Ativa without access in 30 days, pending support request), returns only church id/name/status (B10), thresholds in `HEALTH_THRESHOLDS`, 2 min in-memory cache. Rejected e-mails come from the Resend webhook (`src/modules/webhooks/`: Svix signature checked by hand on the raw body, `EmailEvent` once per `svix-id`, church resolved by e-mail) and show on the church Users tab (`emailRejectedAt`). Team e-mails by role in `src/lib/team-emails.ts` with `teamRecipients(roles)` (ADMINISTRADOR always included): requests awaiting the iEzer, decisions to the requester (`notifyRequesterDecision` in `acesso/suporte/service.ts`), and a church left without admin (from `notifySuspension`).
- `src/lib/prisma.ts` exports a singleton `PrismaClient` (cached on `globalThis` outside production).

### Feature slice pattern

Every CRUD section (e.g. `src/modules/financeiro/contas-a-receber/`, `src/modules/cadastro/fornecedores/`) has the same five files — copy an existing one when adding a section:

- `schemas.ts` — Zod schemas for body/params/query plus inferred types. Messages in Portuguese. IDs validated as `cuid()`. Empty strings preprocessed to `undefined`.
- `repository.ts` — the only layer that touches `prisma`; builds `where` filters (always `organizationId: { in: organizationIds }`), `include`s relations, converts amounts to `Prisma.Decimal`; write methods take an optional `db` (transaction client).
- `service.ts` — business logic and DTO mapping (`Decimal` → number, `Date` → ISO string, flattened relation names like `categoryName`). Receives `RequestContext`; writes run inside `runAudited` and log before/after DTOs; creates use `requireWriteOrganization`. Throws a custom `XxxNotFoundError`.
- `controller.ts` — class with arrow-function handlers; parses input with the schemas, catches the not-found error and returns `reply.notFound(...)`.
- `routes.ts` — instantiates repository → service → controller at module load and wires the endpoints; registered in the parent module's `routes.ts`.

List endpoints return `{ items }`. Payables/receivables support recurrence (creating N installments sharing a `recurrenceGroupId`, delete with `?scope=series`) and settlement (`PATCH /:id/baixar`).

### Database

Schema in `prisma/schema.prisma`; migrations in `prisma/migrations/` are hand-named by date (`YYYYMMDD_description`), starting from `20260801_baseline`. Write data-preserving SQL by hand (renames, backfills) instead of trusting `migrate diff` blindly. Enum values are Portuguese (`PENDENTE`, `PAGO`, `RECEBIDO`, `MENSAL`...).

- `Organization` is two-level (sede → congregações via `parentId`); `status` (IMPLANTACAO, ATIVA, SUSPENSA, ENCERRADA) only matters on the sede; CNPJ (numeric or alphanumeric, stored unpunctuated and uppercase) is unique among sedes (partial index). `OrganizationContact` holds the account owner and LGPD officer. Every business table has a required `organizationId`; repositories take the request's organization ids (`DEFAULT_ORGANIZATION_ID` in `src/lib/organization.ts` is only a script default).
- `Person` (formerly `Member`) is the people table, served by `src/modules/pessoas/` (`/pessoas`): bond (vínculo) and status (situação) are separate enums; minimum fields per bond and the under-18 guardian/consent rule live in `pessoas/rules.ts`. `Family`/`FamilyMember` (one family per person; `pessoas/familias/` checks on every change that no minor is left without a guardian; `Family.primaryContactPersonId` is the first adult by entry order (`FamilyMember.createdAt`, `firstAdult` in `rules.ts`), passed on when they leave, settable to anyone; the household address is the primary contact's, only a suggestion copied with `useFamilyAddress` or `PATCH /familias/:id/endereco` to the people chosen; family member DTOs hide contact/address of people from unread orgs, so `mapDetail` takes `readOrganizationIds`; a family is visible when it belongs to a read org or has someone from one, and `GET /familias` lists them paginated with search by family or member name), `PersonRelation` (Sprint 24, `pessoas/parentes/`, `/pessoas/:id/parentes`): kinship apart from the household, only `PAI_MAE` (`personId` is parent of `relativeId`) and `CONJUGE` (pair stored in id order, CHECK with `COLLATE "C"`); siblings, grandparents and grandchildren are derived; rules (no self, no cycle via recursive CTE, max two parents, one non-deceased spouse, one link per pair) in the service; relatives from unread orgs come with name only; it never counts as guardian (RF-F15) and blocks "Apagar registro"; `FamilyMember` DTO exposes in-household `parentIds`/`spouseId`. `FollowUp` + `PersonEvent` (timeline; bond/status change only through `pessoas/ciclo-vida/` endpoints, which also suspend the person's user via `src/modules/acesso/suspensao.ts`; Painel counters in `pessoas/pessoas/jornada.ts`), `PersonConsent`, `ChurchListItem` (church lists stored on the sede; `npm run pessoas:seed`). Receivables expose `personId`/`personName` (`/cadastro/membros` was removed in Sprint 5). Import by template spreadsheet in `pessoas/importacao/` (`exceljs`; template with hidden `_meta` version, preview without writes, atomic confirm with batched `createMany` and app-generated ids from `src/lib/ids.ts`, `runAudited(..., { timeout })`).
- `User`, `Session`, `Account`, `Verification`, `TwoFactor` follow the Better Auth schema (email/password login since Sprint 2); `User.personId` is optional and unique. `AuditLog` has author, org, target, before/after, IP, user agent and `personIds` (people affected); every write goes through `runAudited` (`src/lib/audit.ts`, `maxWait` 10 s; log-only entries such as support reads use `recordAudit`, a plain insert without a transaction), which keeps only changed fields when both before and after are given (RF-LP05) and derives `personIds` (pass `personIds` when the entry touches people it can't infer, e.g. a family rename). Login, failed login and logout are logged from Better Auth hooks in `src/lib/auth.ts`. The table is append-only (SQL trigger): UPDATE/DELETE/TRUNCATE fail, except deleting LOGIN rows older than 12 months. Labels for actions/fields shown in Configurações › Auditoria and the CSV export live in `src/modules/acesso/auditoria/rotulos.ts` — add new action keys there. Interactive `$transaction` works on the pooler.
- `AccessProfile` (owned by the sede, `factoryKey` for factory profiles) + `AccessProfilePermission` (catalog keys) + `UserAssignment` (user × profile × organization).
- `Invite` + `InviteAssignment`: token stored only as SHA-256 (`src/lib/tokens.ts`), 72h, single use; resend swaps the hash. One pending invite per e-mail (partial unique index in SQL). Accepting creates User + credential Account + assignments in one `runAudited` (outside Better Auth), then signs in via `auth.api.signInEmail`. Login e-mail is unique across churches (RF-CV08, `assertLoginEmailAvailable`). Password rules beyond length/HIBP (no e-mail, no church name) in `src/lib/password-rules.ts`.

## Rules

- Every route checks permission on the server; hiding things in the front is only UX.
- Civil dates (birth, admission, conversion) are `@db.Date`, never `DateTime`; the API reads/writes them as `"YYYY-MM-DD"` (`src/lib/civil-date.ts`).
- Phones are stored as digits with country code (`normalizePhone`, `src/lib/phone.ts`) for Mensageria; the front masks them for display (exception to the front's `PhoneInput` pattern). CPF stored as 11 digits, check digit validated (`src/lib/cpf.ts`).
- The user tests visually in the browser — don't run Playwright/screenshots unless asked.
- The church app and the team back-office app share the API session cookie in every environment: signing in on one replaces the session of the other. When testing both, use a separate browser profile per app.
- To undo a change, revert it by manual edit — never `git checkout`/`reset`/`restore` on files with uncommitted work.
- There is a single Supabase database (free plan, no backups) shared by local dev and the Render deploy. Any command that can reset or wipe it (`prisma migrate reset`, `migrate dev`, `db push --force-reset`, `migrate diff --shadow-database-url`, DROP/TRUNCATE) must be asked first and wait for confirmation. Apply migrations with `prisma migrate deploy`; draft SQL with `migrate diff --from-schema-datamodel <old schema copy> --to-schema-datamodel prisma/schema.prisma --script`.
